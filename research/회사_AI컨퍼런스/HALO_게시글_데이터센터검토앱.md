**[Summary | 한 줄 소개]**
협력업체 계약 전이라 검토를 기다려야 했던 데이터센터 초기 설계에서, 설계 실무자가 Claude Code로 전력 이중화·데이터홀 단면·발전기실 급·배기 검토 앱 3종을 직접 만들어 조건만 넣으면 근거와 함께 규모를 바로 확인하도록 했습니다.

## ① Background & Objective | 배경 및 목적

**해결하고자 한 문제**
- 데이터센터는 전기실, 발전기실, 데이터홀, 냉동기 등 설비·전기 공간의 비중이 커서, 이 공간들의 규모가 건물 전체의 평면·입면·층고를 좌우합니다.
- 그런데 초기 기획·계획설계 단계에는 전기·설비 협력업체와 계약이 되어 있지 않은 경우가 많아, 유사 사례로 추정하거나 업체에 비공식적으로 검토를 부탁하고 회신을 기다려야 했습니다.
- 이후 정식 검토 결과가 초기 가정과 다르면 전기실 규모, 발전기실 그릴창 면적, 데이터홀 층고가 바뀌어 설계 변경과 재작업이 생겼습니다.

**목표**
- 협력업체와 협의하며 메모해 둔 검토 방법과 장비 사양을 도구로 정리해, 설계자가 업체 검토 전에도 근거 있는 수치를 바로 확인할 수 있게 하는 것
- 개인의 경험에 흩어져 있던 전문 지식을 팀이 함께 쓰는 도구로 만드는 것

## ② Approach & Process | 활용 방법 및 과정

**활용 도구**
- **Claude Code (Anthropic)**: 자연어로 기능과 계산 조건을 설명하면 AI가 코드를 작성 (바이브 코딩)
- **GitHub**: 버전 관리 / **Vercel**: 웹 배포 (링크로 바로 접속)
- 화면은 HTML·CSS·JavaScript, 사례 C는 React

**제작 과정**
1. **지식 정리** — 협력업체 협의 메모, 장비 사양, 계산 근거, 전문가의 검토 순서를 입력·규칙·산식 형태로 정리
2. **검토 항목 선정** — 건축 규모에 영향이 가장 큰 3가지(전력 이중화, 데이터홀 단면, 발전기실 급·배기)를 우선 선정
3. **AI로 개발** — Claude Code에 요구사항을 말로 설명 → 생성된 코드를 실행 화면으로 확인 → 수정 반복
4. **배포와 개선** — GitHub에 커밋하고 Vercel로 배포, 팀원과 협력업체의 의견을 받아 다시 AI로 반영하는 순환 (사례 A 기준 73회 업데이트)

**만든 앱 3종**

| 앱 | 입력 | 결과 → 공간 영향 |
|---|---|---|
| A 전력 이중화 검토 | 이중화 방식(7종), IT 용량, 변압기 용량 | 변압기 대수·부하율, 전기실 구성, 급전 다이어그램 → 평면 |
| B 데이터홀 단면 검토 | 서버 수량, 랙 배치, 기둥 간격, 랙 부하 | 필요 풍량, 보 아래 환기 공간, 입면·단면·평면 → 층고·규모 |
| C 발전기실 급·배기 계산 | 발전기 제조사·모델, 대수 | 급·배기 개구 면적, 풍속, 계통도 → 입면·층고 |

## ③ Results & Impact | 결과 및 성과

**주요 결과물**
- 웹 기반 검토 앱 3종 (아래 체험 링크)
- 계산식을 화면에 그대로 표시: 예) 변압기 유효용량 4,000 × 0.99 × 0.9 × 0.96 = 3,421.4kW
- 결과를 급전 다이어그램, 평면·단면·입면, 급·배기 계통도로 자동 표현
- 부하율 초과, 풍속 초과, 기둥 간섭 등 자동 경고

**실제 업무 적용**
- 데이터센터 프로젝트의 초기 검토에 시범 적용 중이며, 동료 실무자가 사용하고 협력업체가 앱의 검토 결과를 보며 의견을 주는 방식으로 활용하고 있습니다.

**개선 효과**
- 검토 회신 대기: [○일] → 즉시 확인 *(체감 기준, 직접 입력)*
- 대안 비교: 조건(이중화 방식, 랙 밀도, 발전기 대수)을 바꾸면 바로 재계산
- 일관성: 같은 입력이면 누가 해도 같은 결과
- 설명력: 산식과 출처를 함께 보여 주어 발주처·협력업체와 협의할 때 근거로 활용

## ④ Lessons Learned | 주요 인사이트

**효과적이었던 점**
- **핵심은 코딩 실력이 아니라 업무 지식**: AI가 코드를 쓰고, 실무자는 "무엇을 어떻게 검토하는지"를 정확히 설명하는 데 집중하면 됩니다.
- **결과는 숫자보다 도면으로**: 설계자에게는 계산표보다 평면·단면으로 보여 주는 것이 판단에 훨씬 빠릅니다.
- **작게 만들고 자주 배포**: 하나의 큰 프로그램보다 검토 항목별 작은 앱(Micro-App)으로 나누니 만들고 고치기가 쉬웠습니다.

**시행착오와 한계**
- AI가 만든 계산이 맞는지는 AI가 보증하지 않습니다. 다른 LLM으로 크로스체크하고 유사 사례 결과와 비교해 확인했으며, 기준 사례 시험을 앱에 넣어 자동 확인하는 체계가 다음 과제입니다.
- 기준값 중 일부는 출처가 화면에 표시되지 않아, 확인된 값과 가정한 값을 구분해 보여 주는 작업이 필요합니다.
- 같은 냉각 산식이 두 앱(A·B)에 따로 들어가 있어, 공통 지식은 한곳에서 관리해야 한다는 것을 배웠습니다.
- 제조사 카탈로그 기반 데이터는 분기별로 최신화가 필요합니다.
- 결과는 개략 검토용이며, 협력업체의 상세 검토를 대체하지 않습니다.

**다음 단계**
- 앱들을 하나로 묶고, 온톨로지로 설비와 공간의 관계를 정리한 뒤 AI 에이전트가 앱을 호출해 "수전용량이 바뀌면 전기실·발전기실·데이터홀이 어떻게 바뀌는지"를 근거와 산식이 담긴 검토의견서로 만들어 주는 시스템을 목표로 합니다.
- 데이터센터뿐 아니라 산업시설, 방송통신시설 등 설비 비중이 큰 시설로 확장할 수 있습니다.
