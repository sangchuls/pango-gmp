[사례명 / 프로젝트명]
DC Review Micro-Apps — 설계자가 직접 만든 데이터센터 초기 설계 검토 앱

[Summary | 한 줄 소개]
협력업체 계약 전이라 검토를 기다려야 했던 데이터센터 초기 설계에서, 설계 실무자가 Claude Code로 전력 이중화·데이터홀 단면·발전기실 급·배기 검토 앱 3종을 직접 만들어, 조건만 입력하면 산식과 도면으로 규모를 바로 확인할 수 있게 했습니다.


① Background & Objective | 배경 및 목적

해결하고자 한 문제
· 초기 기획·계획설계는 구조·기계·전기 분야의 프로젝트 팀이 구성되기 전 단계라, 건축가가 경험과 사례로 기술 조건을 판단해야 합니다.
· 사무실·주거처럼 사람이 머무는 공간이 중심인 일반 시설과 달리, 데이터센터 같은 특수 시설은 전기실·발전기실·데이터홀 등 설비 공간의 비중이 커서 이 규모가 건물의 평면·입면·층고를 좌우합니다. (서버실 층과 기계·전기실의 면적이 일반적으로 1:1 수준)
· 계약 전이라 협력업체에 비공식으로 검토를 부탁하고 회신을 기다려야 했고, 나중에 정식 검토 결과가 다르면 규모가 바뀌어 설계 변경과 재작업이 생겼습니다.

AI 활용 배경과 목표
· AI 코딩 도구로 비개발자도 업무 도구를 직접 만들 수 있게 되었습니다.
· 협력업체와 협의하며 메모해 둔 검토 방법, 장비 사양, 전문가의 검토 순서를 도구로 옮겨, 업체 검토 전에도 근거 있는 수치를 바로 확인하는 것이 목표입니다.
· 개인의 경험에 흩어져 있던 전문 지식을 팀이 함께 쓰는 도구로 남기는 것도 목표입니다.


② Approach & Process | 활용 방법 및 과정

활용 도구·기술
· Claude Code (Anthropic) — 자연어로 기능과 계산 조건을 설명하면 AI가 코드 작성 (바이브 코딩)
· GitHub — 버전 관리 / Vercel — 웹 배포 (설치 없이 링크로 접속)
· HTML·CSS·JavaScript (사례 C는 화면을 React로 구성)

개발 과정 (워크플로)
1. 지식 정리 — 협력업체 협의 메모, 장비 사양, 계산 근거를 "입력값 → 규칙·산식 → 결과" 형태로 정리
2. 검토 항목 선정 — 건축 규모에 영향이 큰 3가지(전력 이중화, 데이터홀 단면, 발전기실 급·배기)를 우선 선정
3. AI로 개발 — 필요한 기능과 산식을 말로 설명 → AI가 코드 작성 → 실행 화면으로 확인하며 수정 반복
4. 배포와 개선 — GitHub에 저장하고 Vercel로 배포, 팀원·협력업체 의견을 다시 AI로 반영 (개발 기간 2026.05~11, 사례 A 기준 73회 업데이트)

프롬프트 예시 (요지)
· "이중화 방식(N+1, 2N 등)과 변압기 용량을 입력하면 필요한 변압기 대수와 부하율을 계산하고, 계산식을 화면에 그대로 보여 줘"
· "결과를 전기실과 서버 구역의 급전 다이어그램으로 그리고, 부하율이 100%를 넘으면 붉게 경고해 줘"

만든 앱 3종
· A 전력 이중화 검토 — 이중화 방식(7종)·IT 용량·변압기 용량 입력 → 변압기 대수, 전기실 구성, 급전 다이어그램 (공간 영향: 평면)
· B 데이터홀 단면 검토 — 서버 수량·랙 배치·기둥 간격·랙 부하 입력 → 필요 풍량, 보 아래 환기 공간, 입면·단면·평면 (공간 영향: 층고·규모)
· C 발전기실 급·배기 계산 — 발전기 제조사·모델·대수 입력 → 급·배기 개구 면적, 풍속, 계통도 (공간 영향: 입면·층고)


③ Results & Impact | 결과 및 성과

주요 결과물
· 웹 기반 검토 앱 3종 (⑤ 체험 링크)
· 계산식을 화면에 그대로 표시 — 예: 변압기 유효용량 4,000 × 0.99 × 0.9 × 0.96 = 3,421.4kW
· 결과를 급전 다이어그램, 평면·단면·입면, 급·배기 계통도로 자동 표현
· 부하율 초과, 풍속 초과, 기둥 간섭 등 자동 경고

실제 업무 적용
· 데이터센터 프로젝트의 초기 검토에 시범 적용 중이며, 동료 실무자가 사용하고 협력업체가 앱의 검토 결과를 보며 의견을 주는 방식으로 활용하고 있습니다.

정성·정량 성과
· 검토 회신 대기: [ ○일 ] → 즉시 확인 (체감 기준)
· 조건(이중화 방식, 랙 밀도, 발전기 대수)을 바꾸면 바로 재계산하여 대안 비교
· 같은 입력이면 누가 해도 같은 결과 (검토의 일관성)
· 산식과 출처를 함께 보여 주어 발주처·협력업체 협의 때 근거로 활용

자체 점검 결과 (지식 명시화 · 도구 구현 · 검증 · 공유 4개 관점, 11개 항목)
· 세 앱 모두 충족: 검토 영역, 변수·단위 입력, 산식·규칙 근거, 공간 표현, 문서-코드 일치, 배포·접근
· 앱별 충족 항목: A 7개, B 7개, C 8개 / 미흡 항목 없음
· 보완 필요: 기준값 근거 표시(A·B), 기준 사례 시험(A·B), 의견 수집 이력(공통)


④ Lessons Learned | 주요 인사이트

효과적이었던 접근
· 핵심은 코딩 실력이 아니라 업무 지식입니다. AI가 코드를 쓰고, 실무자는 "무엇을 어떤 순서로 검토하는지"를 정확히 설명하는 데 집중하면 됩니다.
· 결과는 숫자보다 도면으로 보여 주세요. 설계자에게는 계산표보다 평면·단면이 훨씬 빠르게 읽힙니다.
· 큰 프로그램 하나보다 검토 항목별 작은 앱(Micro-App)으로 나누니 만들고 고치기가 쉬웠습니다.
· 산식을 화면에 드러내면, AI가 만든 계산이라도 사람이 따라가며 확인할 수 있습니다.

시행착오와 한계
· AI는 계산이 맞는지 보증하지 않습니다. 다른 LLM 크로스체크와 유사 사례 비교로 확인했고, 기준 사례 시험을 앱에 넣어 자동 확인하는 것이 다음 과제입니다.
· 기준값 일부는 출처가 화면에 표시되지 않아, 확인된 값과 가정한 값을 구분해 보여 주는 작업이 필요합니다.
· 같은 냉각 산식이 두 앱(A·B)에 따로 들어가 있어, 공통 지식은 한곳에서 관리해야 한다는 것을 배웠습니다.
· 제조사 카탈로그 기반 데이터는 분기별로 최신화가 필요합니다.
· 결과는 개략 검토용이며 협력업체의 상세 검토를 대체하지 않습니다.

다음 단계
· 지금: 앱 3종이 각각 계산 (시범 적용)
· 다음: 앱 통합, 공통 산식·기준값 정리, 사내 공유
· 목표: 온톨로지로 설비와 공간의 관계를 정리하고, AI 에이전트가 앱을 호출해 "수전용량이 바뀌면 전기실·발전기실·데이터홀이 어떻게 바뀌는지"를 근거와 산식이 담긴 검토의견서로 작성
· 산업시설, 방송통신시설 등 설비 비중이 큰 다른 시설로 확장 가능

공유하고 싶은 경험
· 반복되는 검토가 있다면, 그 검토의 입력·산식·결과를 한 장에 적어 보는 것부터 시작해 보세요. 그 한 장이 앱의 설계도가 됩니다.
